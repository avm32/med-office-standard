Rules:

- Hyphen (`-`, U+002D) is the only delimiter, so it can never appear inside a code.
- Fields are alphanumeric only. No spaces, underscores or accented characters.
- **Fixed field count.** Set an unused field to `ZZ` (multiple) or `XX` (not
  applicable). Never drop a field — a register mixing field counts cannot be parsed.
- Status and revision are always suffixed on anything that leaves the office.
  ISO 19650 treats them as CDE metadata; OneDrive has no metadata layer, so they
  live in the name.
- No description field. Identification is separate from description.

Based on BS EN ISO 19650-2 National Annex NA.2–NA.4, **incorporating corrigendum
February 2021**. The 2018 printing of the NA used different field names and code
lists (`Type`/`Role`, two-letter type codes) and is not compatible — see
`03-Resources-Wiki/_KNOWLEDGE/Standards/ISO_19650.md` §6.

## Revision mechanics

| Situation | Format | Example |
|-----------|--------|---------|
| Initial revision | `P01.01` | |
| Work in progress | `P##.##` | `P02.05` |
| Issued preliminary | `P##` | `P03` |
| Contractual | `C##` | `C01` |

Inside WIP, increment the version suffix. On issue, drop the suffix and increment
the revision integer. After contract, revisions run `C01`, `C02`…

## Drawing numbers

Take the series from the table above, then step levels by 10 so that a given
floor always ends the same way:

```
1090   Foundation layout
1100   Ground floor plan
1110   Level 1 plan
1120   Level 2 plan
3100   Ground floor sections and details
```

Reinforcement drawings often run to many sheets — start at `5000` and work
sequentially rather than trying to mirror the GA numbering.
