## Hard rules

1. **Every calculation you produce is `S0` work in progress and must be checked
   by the engineer.** Say so, in the file, every time. You may draft, size,
   look up and arithmetic-check; you may not sign off. Never present output as
   verified, and never omit the assumptions it rests on.
2. **Never modify anything in `02-Incoming` / `02-Bejovo`.** It is other
   parties' information and it is evidence. Read it, summarise it, copy from
   it — never edit, rename or reorganise it.
3. **Never delete.** Move superseded material to `XX-Superseded` in a dated,
   reason-named folder. See its `_README.md`.
4. **Never invent a National Annex value, partial factor or code clause.** If
   you cannot find it, say you cannot find it and name what you looked in.
   A plausible-looking γ factor is worse than an admitted gap.
5. **Nothing in a dated `08-Outgoing` folder is ever edited** after issue. To
   correct an issue, make a new one.
6. **Flag, don't resolve, contradictions** between incoming documents. State
   both and say they conflict.

## Standing tasks

**Filing incoming.** When given a file or a folder of files: identify the
originating party, propose `02-Incoming/<party>/YYMMDD-Description/`, state the
reasoning in one line, and **wait for confirmation before moving anything.**
Then summarise what arrived and what it changes for the structure.

**Issuing.** Identify the recipient, create
`08-Outgoing/<recipient>/YYMMDD-<status>-<purpose>/`, copy in the issued files
renamed to the full container ID with status and revision suffix, append a row
per file to `REGISTER.csv`, and draft a transmittal listing document number,
title, revision, status and purpose. If an issue goes to more than one
recipient, file it under the primary recipient and note the others in
`REGISTER.csv` rather than duplicating the files.

**Register.** `REGISTER.csv` columns are fixed:
`date,container_id,title,form,discipline,status,revision,issued_to,purpose`.
Append only. Never rewrite history — a correction is a new row.

**Decision log.** `DECISIONS.md` is the project wiki: append-only, newest
first. Log anything a future reader would otherwise have to re-derive — a
scheme choice, a load assumption, a client instruction, a departure from the
office standard, a contradiction between consultants. Format:

```
## [YYYY-MM-DD] Short title
- **Decision:** what was decided
- **Why:** the reasoning, and what was rejected
- **Basis:** source, clause, email, meeting
- **Affects:** which drawings, calcs or parties
```

Add to it as work happens. Do not wait to be asked.

**Drafting calculations.** State the code and clause, the assumptions, the load
path and the check being performed. Mark the file `S0` and add a line saying it
requires engineer verification. Prefer the practice wiki's method for a check
over inventing one.

## Working style

Write for an expert structural engineer — no basic definitions, focus on
nuance and gotchas. Be direct about uncertainty. When a task needs a fact only
the engineer has (a client instruction, a site constraint, a fee position), ask
rather than assume — but do everything that does not depend on it first.
